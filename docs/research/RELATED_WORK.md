## Verified limitations and overlap

ALPS remains the verified overlap for learned, user-space policy feeding Linux scheduling. The second pass additionally opened LAKE's author-hosted paper: it already describes CPU/GPU policy switching by predicted acceleration profitability, kernel inference through a user-space daemon, and the need to include transfer/acceleration cost and resource contention. Its measured system used Linux 6.0 and two A100 GPUs; authors explicitly say benefits depend on subsystem, workload, and hardware. Heracles separately verifies multi-resource feedback allocation in production data-center servers, but its RAPL readings are CPU socket power and its DRAM-bandwidth model requires offline profiling.

## HARM 的定位（不主张首创性）

HARM does not claim novelty for user-space scheduling control (ALPS is directly verified; ghOSt's official implementation repository confirms the architecture, although its paper PDF remained inaccessible), kernel accelerator offload with CPU fallback and cost/profitability policy (LAKE directly verifies this overlap), or cost-aware prediction skipping (SkipPredict; Russell and Wefald's primary paper remains inaccessible). These similarities are overlap, not proof of equivalence. The smallest defensible research question is: **On a user-delegated Linux cgroup, does a controller that predicts only when a conservative estimate of allocation benefit exceeds measured observation/inference/actuation cost improve paired end-to-end net benefit over native allocation and a predict-always policy, without breaching pre-registered latency/safety bounds?** Test with matched native / always-predict / cost-gated trials, charge CPU time and latency to each acquisition/inference/actuation term, capture PSI and cgroup outcomes, and report energy only if full-machine measurement is available. Linux affinity/uclamp are interfaces for CPU placement/performance hints, not by themselves a P/E-core guarantee. This is a question for an experiment, not a novelty or outcome claim.
